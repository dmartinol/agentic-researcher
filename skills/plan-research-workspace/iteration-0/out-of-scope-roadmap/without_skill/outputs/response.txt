RESEARCH PLAN
=============

1. TOPIC
--------
Building an installable, portable agentic research system for planning, executing,
documenting, and verifying evidence-based research.

2. RESEARCH OBJECTIVES
----------------------
Primary objective: Design and validate an architecture for an agent-based research
system that can:
- Support researchers in clarifying objectives and scope
- Create actionable research plans
- Initialize and manage research workspaces
- Execute independent research tasks (including parallel work)
- Record evidence-backed findings with provenance
- Synthesize dependent findings
- Preserve research state across sessions
- Verify evidence and external artifacts
- Support explicit completion workflows

3. RESEARCH SCOPE
-----------------

INCLUDED:
- Agent architecture patterns and standards (Agent Plugins v1, Agent Skills)
- Multi-agent coordination and lifecycle orchestration
- Evidence model design (claims, sources, provenance, freshness)
- Subsystem abstraction layer (ticketing, document store, repository, identity)
- Provider integration patterns (Jira, Confluence, Git)
- Research memory persistence and retrieval
- Workflow safety and mutation rules
- Greenfield vs. existing research project handling
- Portable vs. host-specific component boundaries
- MCP integration patterns
- Research synthesis and contradiction detection

EXCLUDED:
- Host-specific adapter implementations
- Binary database indexing strategies (unless for retrieval layer)
- Authentication implementation details
- IDE-specific features beyond agent definitions
- Numeric confidence scoring systems

4. KEY RESEARCH QUESTIONS
--------------------------
Q1: How can agent definitions remain portable across hosts while supporting
    specialized multi-agent workflows?

Q2: What is the optimal boundary between generic research skills and
    provider-specific specializations?

Q3: How should research memory be structured to support both human readability
    and efficient agent retrieval?

Q4: What verification mechanisms ensure external mutations (Jira, Confluence)
    succeed as intended?

Q5: How can the system support resumability across context windows and agent sessions?

Q6: What evidence model best balances rigor with practical agent execution?

5. RESEARCH PHASES
------------------

Phase 1: Standards and Architecture Analysis (2 weeks)
- Review Agent Plugins v1 and Agent Skills specifications
- Analyze portable vs. host-specific boundaries
- Design subsystem capability contracts
- Define agent orchestration patterns

Phase 2: Evidence Model and Memory Design (2 weeks)
- Design claims/sources/episodes schema
- Define evidence labels and provenance tracking
- Create contradiction detection patterns
- Design memory persistence and retrieval strategies

Phase 3: Provider Integration Patterns (2 weeks)
- Document Jira integration patterns
- Document Confluence integration patterns
- Design MCP integration approach
- Define provider-specific vs. generic skill boundaries

Phase 4: Lifecycle and Safety Design (1 week)
- Define lifecycle state transitions
- Design mutation approval workflows
- Create idempotent initialization patterns
- Design greenfield vs. brownfield detection

Phase 5: Validation and Refinement (1 week)
- Create validation test suite
- Document architecture patterns
- Refine templates (RESEARCH.md, STATE.md)
- Create demonstration examples

Total Research Duration: 8 weeks

RISK ASSESSMENT
---------------

High Risks:
1. External system API changes (Jira, Confluence)
   Mitigation: Abstract behind subsystem capability layer

2. Agent portability across hosts
   Mitigation: Strict adherence to Agent Plugins v1, extensive validation

3. Context window limitations for long research sessions
   Mitigation: Robust STATE.md design, memory persistence

Medium Risks:
1. Evidence model complexity vs. usability
   Mitigation: Iterative refinement with user testing

2. Mutation safety and verification overhead
   Mitigation: Clear approval gates, idempotent operations

3. Greenfield vs. brownfield detection accuracy
   Mitigation: Conservative discovery rules, user confirmation

Low Risks:
1. Documentation quality
   Mitigation: Dedicated technical writer

2. Test coverage
   Mitigation: QA engineer from start
